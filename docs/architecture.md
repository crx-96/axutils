# 架构与兼容契约

本文是本仓库后续开发的架构基线：以发布包划分边界，包内按功能组织，复杂功能在本地拆分，共同机制按使用范围复用。适用于现有包、新增包和范围内重构；具体包的功能与行为差异在其 AGENTS.md 中维护。

## 目录与职责

```text
axutils/
├─ packages/<name>/           发布单元；每个直接子目录有自己的 package.json
│  ├─ AGENTS.md               本包功能地图、特有契约及根规则入口
│  ├─ README.md               使用者入口与详细文档链接
│  ├─ package.json            公共路径、依赖与发布清单
│  ├─ tsconfig*.json          源码、测试与声明构建的配置入口
│  ├─ src/
│  │  ├─ index.ts             包的根入口
│  │  ├─ <feature>/           功能实现与按需拆分的内部文件
│  │  ├─ internal/<domain>/   包内多个功能共用的机制，按需建立
│  │  ├─ node/               显式 Node 能力，按需建立
│  │  ├─ types/              缺少上游声明的第三方类型补充，按需建立
│  │  └─ umd.ts              UMD 聚合入口，仅在提供 UMD 时建立
│  ├─ test/                  按功能、行为分组的源码单元测试
│  │  └─ helpers/            多组测试共用的工具，按需建立
│  ├─ test-browser/          真实浏览器消费页面、测试与配置，按需建立
│  ├─ scripts/               包级构建入口及该包的消费验证
│  │  ├─ smoke/              行为契约与独立导出快照
│  │  └─ consumer/           最小 peer 映射与类型消费用例
│  └─ dist/                  构建产物，不手工编辑
├─ scripts/                  跨包调度与共享工具链
│  ├─ build/                 入口派生、打包和声明转换
│  └─ test/                  根工具链测试
├─ docs/
│  ├─ architecture.md        架构基线
│  ├─ coding-standards.md    实现质量
│  ├─ development.md         开发环境、验证职责与子包接入
│  ├─ troubleshooting.md     工具、浏览器与编辑器故障排查
│  ├─ releasing.md           版本与发布操作
│  ├─ rules/personal.md      已确认的项目个人偏好
│  ├─ examples/<name>/       按包和公开能力组织的 API 文档
│  └─ skills/<task>/         仓库任务 Skill
└─ 根配置与 .github/         共享工具选项、workspace、版本管理与 CI
```

目录树表示职责和已有布局的扩展方式；标记为按需的目录不预建。工具配置留在工具能发现且有对应 tsconfig 的位置，例如包顶层的 Vitest/Playwright 配置；不为统一外观集中搬入 `config/`。测试、脚本、文档和产物不混入运行时源码。个人命名和格式选择在 [personal](./rules/personal.md) 中维护，本规范只定义结构和契约。

根工具链负责包发现、依赖拓扑调度和与业务无关的构建机制；包内脚本负责本包行为、peer 组合、消费 fixture 与薄构建入口。新增第二个包时，只将已经相同的脚本机制提升到根目录，包名、导出断言和业务类型用例留在本包。

## Workspace 与公共入口

`packages/*` 是发布单元。当前发布包为 [@axutils/common](../packages/common/AGENTS.md)；共享工具配置集中在根目录，包级配置只保留必要差异并继承共享选项。

新能力优先放入职责匹配的现有包。具有独立用途、依赖或运行环境边界，且独立版本与发布带来实际收益时才新增包；文件变长或目录变多本身不构成拆包理由。包间通过已声明的 workspace 依赖及对方 `exports` 导入，不跨包引用 `src`、`internal`、`dist` 或测试文件，不形成包依赖环。

公共入口以 `package.json#exports` 为准，使用命名导出。模块源码导出了某个符号，不代表它已成为包的公共 API。现有公共子路径保持稳定，内部文件移动通过原入口转导出维持兼容；根入口负责选择暴露的能力，不能自动汇总全部功能。

新增或改变公开入口时，同步清单、独立导出快照、最小 peer 映射、产物与类型消费用例、使用文档。删除或调整已有路径、名称、类型、类身份及行为前，说明兼容影响与迁移方式；内部拆分不自动增加公共 API。

## 功能落位与文件拆分

| 情况 | 放置与拆分方式 |
| --- | --- |
| 单一、易理解的工具能力 | 放在所属功能目录的一个文件，直接实现；不强制增加门面和子目录 |
| 一个公开能力包含多种独立职责 | 保留原入口，如 `axios/http.ts`；实现放相邻 `http/` 下，按配置、错误、取消、身份与执行等实际职责拆分 |
| 多个相关 API 具有独立实现与共同配置 | 保留公开门面；例如 `object/json.ts` 只导出 API，`json/parse.ts` 和 `stringify.ts` 各自维护处理流程，`types.ts` 保存双方使用的配置契约 |
| 公开判断或编排包含独立的词法机制 | 将机制留在所属功能内部，如 `check/internal/function-source.ts` 和 `scripts/build/declaration-tokens.mjs`，不把运行时扫描与构建扫描强行合并 |
| 同一功能内多个 API 共用机制 | 放该功能的局部内部目录，如 `date/internal/`；不要先提升为包级共享 |
| 多个功能需要相同机制 | 确认语义和变化原因相同后，放 `src/internal/<domain>/`；已有独立基础能力可直接复用，无需复制 |
| 仅某个平台需要的实现 | 放对应平台目录；当前 Node 能力使用 `src/node/` 和显式 `/node` 公共路径 |
| 类型、常量和错误 | 默认靠近使用者；同一功能有多个使用者或独立契约时再建局部 `types.ts`、`constants.ts`、`errors.ts`，既有命名沿用 |
| 测试与 fixture | 测试按功能和行为组织；单组测试专用 fixture 留在附近，跨组共用工具才放 `test/helpers/` |

拆分以独立修改原因、依赖边界、状态所有权及可验证的职责为依据，不设置文件行数、文件数量或目录深度硬限制。公共编排混入较复杂的词法扫描、序列化或资源管理等机制，导致阅读和修改必须同时理解两层时，可提取内部模块；一个内聚的算法、类型声明或数据表不因行数多而强制拆开。拆分后应能说明每个文件的职责，避免一函数一文件、只有路径转发作用的内部层，以及集中堆放无关代码的 `utils/`、`helpers/` 或全局 `types/`。

提取时确认真实使用者和依赖方向，并比较新增参数透传、状态协调和阅读跳转的成本。能够在原文件内澄清的逻辑不必抽象；已重复且语义相同的机制可以复用，例如 HTTP 的最终头解析和重试头快照，但两种客户端仍各自维护策略和生命周期。

薄转导出门面只组织导出；简单入口可以直接承载实现，无需先改成门面。内部实现优先直接导入所属模块；包根入口和面向消费者的聚合入口不作为内部依赖。已有 `date/internal.ts` 这类局部聚合有明确作用时可保留，下面的实现文件不能反向引用它。

## 职责与依赖方向

```text
公共入口 → 功能实现 → 功能内机制 / 包内共享机制 → 基础能力与已声明依赖
Node 实现 → 不依赖宿主的通用机制
测试、构建与消费验证 → 源码或公开产物（按验证目的选择）
```

- 功能实现维护自己的策略与生命周期，共享机制不能反向依赖消费它的客户端。允许有方向的基础能力复用，例如 HTTP 身份计算使用 JSON 和摘要；不能让这些基础能力再依赖 HTTP。运行时模块不形成循环依赖。
- `internal` 表示包的实现细节，不保证零第三方依赖。共享模块可依赖已声明的 peer 或基础功能，但调用入口需要承担完整的传递依赖；无 peer 入口不得经转导出、类型引用或共享模块引入可选 peer。实际边界同时核对运行时和声明引用图。
- 通用实现不依赖 `node/`、Node 内置模块或仅由 Node 提供的全局能力；浏览器专有能力在使用边界探测，避免导入时要求 DOM。Node 实现可以复用不依赖宿主的通用机制，显式选择方式不替换成隐式平台切换。
- 运行时源码不引用 `test`、`test-browser`、`scripts` 或生成的 `dist`。共享类型靠近所属功能；只有类型的反向引用不会产生运行时环，但持续联动或开始引入运行时符号时，应移到双方可依赖的局部类型文件。
- 不因文件形状相似而统一平台值语义、错误结构或异步生命周期。common 的具体差异以[本包功能与契约](../packages/common/AGENTS.md#功能与契约)为准。

默认根入口不加载可选 peer，第三方适配由精确的功能子路径提供；新包如有不同的定位与依赖承诺，在包级契约中明确。每个包的 `scripts/consumer/peers.json` 为各公共入口声明最小 peer 集合，隔离消费检查负责验证该承诺。

## 构建与声明

包级 `scripts/build.mjs` 调用根 `scripts/build/package.mjs` 的 `buildPackage(packageRoot, options)`，仅提供包目录和可选 UMD 配置。共享脚本从 exports 的 ESM 产物目标定位源码，例如 `./date` 指向 `dist/date/index.js`，再对应 `src/date/index.ts`。不在包级脚本另外维护入口清单。

每个 exports 项显式提供 `import.types/default` 和 `require.types/default`，同一 stem 分别对应 `.d.ts/.js` 与 `.d.cts/.cjs`，`types` 排在 `default` 前。源码相对模块引用使用 `.js`；内部文件也参与声明引用图，不能只保留公开入口的声明。

每次构建清空本包 dist，依次生成 ESM、CJS、UMD（如声明）和类型。仅 external 已声明依赖与 Node 内置模块，编译器辅助代码随产物打包。UMD 将其入口使用的通用第三方依赖内置，入口与全局名由本包提供，`unpkg`/`jsdelivr` 与实际 UMD 产物一致。兼容目标见[开发环境](./development.md#环境)。

ESM 声明沿 .js 引用解析 .d.ts；CJS 声明沿 .cjs 引用解析 .d.cts。声明词法扫描和模块引用改写各有单一职责：保留裸 peer、注释、普通字符串及模板静态文本，只改写真实模块说明符；模板插值中的 import 类型仍须解析。双格式声明的兼容性由 NodeNext、skipLibCheck:false 下的 ESM/CJS 真实消费检查验证。
